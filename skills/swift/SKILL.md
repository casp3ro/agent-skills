# Swift Best Practices

Production guide for modern Swift on iOS and macOS. Rules are prioritized by impact to guide code generation, review, and refactoring. Toolchain baseline: Swift 6.2+ language mode with Approachable Concurrency (current release: Swift 6.4, Xcode 27).

## When to Apply

Use these guidelines when:
- Writing new Swift code, SwiftUI views, or Swift packages
- Reviewing or refactoring Swift for correctness, safety, or structure
- Fixing Swift 6 concurrency diagnostics (`Sendable`, actor isolation, data races)
- Designing app architecture, module boundaries, or repository layout
- Integrating REST/OpenAPI backends, persistence, push notifications, webhooks, or WebSockets
- Explaining Swift to a developer coming from TypeScript, JavaScript, or Python

## Core Principle

Swift is a progressive-disclosure language. Start with the simplest, most static, single-threaded thing that works, and add dynamism (concurrency, reference semantics, existentials, unsafe code) only where you can name the reason.

| Need | Default | Move down only when |
|---|---|---|
| Data | `struct` / `enum` | You need identity, shared mutation, or a framework requires a class |
| Abstraction | Concrete type | The same code repeats across types → protocol |
| Polymorphism | `some P` / generics | You need heterogeneous storage → `any P` |
| Execution | Main actor, synchronous | Profiling shows a hang → `async` → `@concurrent` → `actor` |
| Safety | Safe APIs | C interop or a measured hot path → `Unsafe*` |

## How to Use

1. When writing code, follow the rules from the highest-priority categories first; concurrency and modeling mistakes are the most expensive to fix later.
2. When reviewing, read the relevant rule files and report violations with the rule ID, for example `concurrency-actor-reentrancy`.
3. When a concept needs explaining (for example "why does this need `await`?"), use the reference primers.
4. Prefer the platform: Foundation, the standard library, SwiftUI, SwiftData, and Swift Testing before third-party packages.

Each rule file contains:
- A short explanation of why it matters
- An incorrect example with an explanation
- A correct example with an explanation
- Notes on edge cases and a reference link
